This report records the PKI Manager v3.19.1 key-store interface and the stock OpenBao 2.7.3 proof of concept from 26 November 2026. The migration plan covers the downstream implementation and its release tests. [Implementation plan](doc-012%20-%20OpenBao-fork-and-PKI-Manager-migration-plan.md)

## 1. Every interaction with the Cosmian KMS

### 1.1 Transport

- KMIP endpoint `POST <KMS_URL>/kmip/2_1`, KMIP 2.1 as JSON TTLV (`backend/src/kms/client.ts`,
  `sendKMIPRequest`). Optional `Authorization: Bearer <KMS_API_KEY>`.
- 30 s timeout, 3 attempts with linear back-off, also on 4xx.
- No batching, no KMIP binary protocol, no TLS client certificate.

### 1.2 Operations seen on the wire

A recording proxy (it logs the shape of each request, with values redacted) sat between the
backend and Cosmian 5.28.0 while the whole backend test suite ran
(`KMS_URL=<proxy> KMS_AVAILABLE=true vitest run`: 1014 of 1015 tests passed, 1 timeout during
the recording). It recorded 731 HTTP requests. Of these, 718 were KMIP POST requests and 13 were successful GET requests to `/version` from the test helper. The SCEP RA operations do not run in that suite (the RA tests
mock the KMS); they are read from `services/ra.service.ts` and were tested on 5.28.0 when SCEP was
built.

`GetAttributes`, `Sign`, `SignatureVerify`, `Decrypt`, `Revoke`, `Destroy`) plus `Query` in the diagnostic client. It does not use `Locate`, `Create`, `Import`, `Register`, `Encrypt`, `ReKey`,
`Export`, batches, Covercrypt, key wrapping, HSM or any of the other Cosmian features.

### 1.3 `Certify`: the only complex operation

`Certify` is the coupling. Three request forms and one follow-up read.

| Form | Request | Used by |
|---|---|---|
| Self-signed CA, key generated by Cosmian | no `UniqueIdentifier`; `Attributes{CertificateType=X509, CryptographicAlgorithm=RSA, CryptographicLength, CertificateAttributes{16 CertificateSubject* + 16 CertificateIssuer* text fields, empty when unused}, vendor x509-extension, vendor requested_validity_days, vendor tag}` + `Subject` | `ca.service.ts:400` |
| Leaf for a KMS key pair | `UniqueIdentifier=<public key>` + `Link{CertificateLink=<CA cert>}` + `Link{PublicKeyLink}` + DN fields + extensions + validity | `certificate.service.ts:863,1104`, `bulk.routes.ts:419,903`, `trpc/procedures/certificate.ts:1620,2032`, `ra.service.ts:123` |
| CSR (key kept) | `CertificateRequestValue=<PEM>`, `CertificateRequestType=PEM`, `Link{CertificateLink}`, no algorithm/length, extensions, validity | `external.routes.ts:471` (Kubernetes issuer, SCEP gateway) |
| Then `Get` | the response holds only the certificate id; the client sends `Get` to read the DER and the `PrivateKeyLink`/`PublicKeyLink` | all of the above |

Cosmian finds the CA private key through the CA certificate's `PrivateKeyLink`, builds the
certificate from an **OpenSSL config string** (`[ v3_ca ]` section, see
`buildCertificateExtensions` in `certificate.service.ts:264`), copies SAN/keyUsage/EKU from a CSR,
and picks the serial number.

Facts found by the spike:

- **Cosmian cannot make an ECDSA X.509 CA** through certify-from-subject: 5.28.0 answers 422
  `do_sigver_init: operation not supported for this keytype` for `ECDSA-P256` and `ECDSA-P384`.
  That is why `keyAlgorithmSchema` (`trpc/schemas.ts:19`) allows only RSA for CAs.
- **The CA certificate exists only in the KMS.** `certificate_authorities` has no PEM column;
  Application code reads certificates through `getCertificate()` at 35 locations (section 1.4).

## 2. The minimum contract

| Capability | PKI Manager uses it for |
|---|---|
| Generate a key with an export policy | RSA-2048, RSA-3072, RSA-4096 and ECDSA P-256 or P-384 keys |
| Import a wrapped key | Preserve the public identity of an existing key during migration when its source policy permits transfer |
| Read the public key | X.509 SubjectPublicKeyInfo, OpenSSH CA public keys and identity checks |
| Sign data or a digest with a specific key version | X.509 certificates and CRLs, SSH certificates and KRLs, and SCEP responses |
| Unwrap a fixed-length CMS session key | SCEP RSA-3072 key transport for AES or 3DES |
| Export an eligible private key as PKCS#8 | Downloads that the product and key policy permit |
| Destroy a key | Remove key material when its owner deletes it |

The backend builds certificates and CRLs and verifies signatures. SQLite stores public certificates and their links to key references. The key store holds the private keys.

## 3. The OpenBao spike

Run on 2026-11-26: OpenBao **2.7.3** (`ghcr.io/openbao/openbao:2.7.3`, dev mode, file audit
device) and Cosmian **5.28.0** (dev stack) on WSL2. Result: **33 of 33 checks passed.**

| # | Check | Result |
|---|---|---|
| 1 | AppRole login, ACL policy `pki-manager` | token works; `GET sys/audit` → 403 |
| 2 | create RSA-2048/3072/4096, P-256, P-384 (`exportable=false`) | all; RSA-4096 0.7–1.2 s, EC ≈ 10–20 ms |
| 2 | export of a non-exportable key | 403 |
| 2 | ACL denies `transit/export/signing-key/ca-*` even for an exportable key | 403 (two independent controls) |
| 3 | self-signed root CA for each of the 5 algorithms, built locally, signed in OpenBao | `openssl verify -x509_strict` OK; `sha256WithRSAEncryption`, `ecdsa-with-SHA256`, `ecdsa-with-SHA384` |
| 4 | leaf with an OpenBao-generated exportable key (RSA by RSA, P-256 by P-384, P-256 by RSA): SAN DNS/IP/email, KU, EKU, CDP, SKI/AKI | `openssl verify -x509_strict` OK; exported PKCS#8 matches; `openssl pkcs12 -export` OK |
| 5 | CSR signing, EC CSR by RSA CA and RSA CSR by EC CA, CSR key and requested extensions kept, `CA:FALSE` added when absent | `openssl verify -x509_strict` OK; SAN preserved |
| 6 | CRL v2 (2 entries, CRL number, AKI) by RSA-4096 and P-256 CAs | `openssl crl -verify`: verify OK |
| 7 | SSH host and user certificates signed by two OpenBao P-256 keys, real `sshd` (non-root) | client trusts host via `@cert-authority`; `sshd`: `Accepted publickey … ECDSA-CERT` |
| 8 | SCEP RA: `sign` with `prehashed=true`, `signature_algorithm=pkcs1v15` over a SHA-256 digest | verifies as RSASSA-PKCS1-v1_5/SHA-256 (same result as KMIP `DigestedData`) |
| 8 | SCEP RA: RSA PKCS#1 v1.5 decrypt in Transit | **gap confirmed**: Transit decrypts RSA with OAEP-SHA256 only (`sdk/helper/keysutil/policy.go:1210` at v2.7.3) |
| 9 | migrate an RSA-2048 and an RSA-4096 CA made by Cosmian (`Get` PKCS8 → Transit `import`, `exportable=false`) | leaf signed by OpenBao verifies against the **Cosmian-issued** CA certificate |
| 9 | migrate a `Sensitive=true` SSH CA key | plain `Get` → `Sensitive: DENIED`; **wrapped `Get`** with OpenBao's wrapping key (RSA-OAEP-SHA256 + AES-KWP, 664 bytes) imported by Transit; same OpenSSH CA key; OpenBao signature verified by Cosmian `SignatureVerify` |
| 10 | latency per signature, sequential, loopback | OpenBao P-256 3–9 ms, RSA-2048 5–10 ms, RSA-4096 11–25 ms; Cosmian P-256 `Sign` 3–8 ms (same order) |
| 11 | audit device | every request logged; the sign input is HMAC-ed, not in clear |


The stock Transit engine passed the signing and key-management checks. The test for SCEP key transport passed because stock Transit refused the required PKCS#1 v1.5 operation. That gap led to the downstream implementation. The transfer checks used synthetic source keys. Existing installations require their own inventory, migration rehearsal and recovery test.
